# BG Company 2.0 기존 시스템 조사와 구현 결과

기존 관제 웹, 데이터 기록 구조, 콘텐츠 파이프라인은 재사용할 수 있다. 새 Director와 작업 큐는 기존 Hermes 및 운영 데이터와 분리해 구현했다. 저장소와 공개 웹 응답은 확인했지만, VPS 내부와 실제 운영 데이터베이스에는 접근하지 못했다. 전수 조사는 접근 가능한 코드 범위에서 수행했으며 운영 환경 조사는 미완료다.

프로젝트 기간은 2026년 10월 11일부터 11월 10일까지다. 이번 작업 범위는 기존 시스템 조사와 안전한 개발 기반의 첫 구현이다.

## 에이전트와 Hermes 의존성

범용 AgentRunner는 `mock`, `hermes`, `hermes-dry-run`을 지원한다. 에이전트 이름이나 관제 상태가 있다는 사실만으로 실제 자율 개발이 구현됐다고 볼 수 없다. 등록 정보에는 정책 엔진, 규칙, Mock 실행기도 섞여 있다.

블로그 콘텐츠 파이프라인은 별도로 `codex` 경로를 지원하며, Planner, Marketing, Writer, QA의 입력과 결과 정규화 코드를 공유한다. Codex 분기는 Hermes 실행을 직접 호출하지 않는다. 따라서 새 사업 개발 큐에 Hermes를 필수 의존성으로 넣을 필요가 없다.

현재 콘텐츠 Codex 브리지는 `gpt-5.6-sol`에 고정돼 있고, 읽기 전용 샌드박스와 JSON 출력 스키마를 사용한다. 파일 개발 실행기로 바꾸지 않고 콘텐츠 전용으로 유지한다. GPT-6 Sol 기반 Builder는 지원 모델과 CLI 인증을 확인한 뒤 별도 격리 실행기로 구현해야 한다.

Codex 콘텐츠 브리지의 기본 연결 주소는 `host.docker.internal:43928`이며 Windows 예약 작업 스크립트도 있다. 실제 실행기가 VPS, 작업 서버 또는 개인 PC 중 어디에 있는지는 확인하지 못했다. 개인 PC를 꺼도 예약 AI 작업이 실행된다는 보장은 아직 없다.

Hermes Bridge는 Compose의 `hermes` 프로필에 있고, 기본 공급자 설정은 OpenAI API다. 이미지 기반은 Hostinger Hermes Agent의 `latest`다. 이번 작업에서는 기존 Bridge를 삭제하거나 유료 호출을 실행하지 않았다. 실제 운영 의존성을 확인하기 전까지 보존하고, 새 큐는 Hermes 없이 운영하도록 결정했다.

근거: `apps/web/src/lib/agents/agent-runner-provider.ts`, `agent-registry.ts`, `apps/web/src/lib/content-pipeline/content-pipeline-service.ts`, `apps/web/src/lib/codex/codex-content-client.ts`, `tools/naver-draft-agent/src/codex-content-bridge.ts`, `services/hermes-bridge/Dockerfile`.

## Docker와 예약 자동화

다음은 실행 중인 컨테이너 목록이 아니라 저장소에 정의된 구성이다.

| 구성 | 소스에서 확인한 내용 | 재사용 판단 |
|---|---|---|
| web | Next.js Dockerfile, 관리자 인증, Traefik 도메인 라벨, PostgreSQL 의존성 | 관제 화면과 인증 재사용 |
| postgres | PostgreSQL 17 Alpine, 호스트 127.0.0.1:5432, 영속 볼륨 | 운영 데이터 보존; 개발은 별도 DB 사용 |
| hermes-bridge | 선택 프로필, 별도 HTTP Bridge | 기존 업무 보존; 신규 큐의 필수 의존성에서 제외 |
| 생성 이미지 볼륨 | `bg_company_generated_stock_blog` | 보존 |
| 블로그 스케줄러 | cron 설치, flock 중복 방지, 보호된 scheduler API, KST 일정 및 재시도 정책 | 정책과 실행 이력 패턴 재사용 |
| 네이버 게시 | 로컬 Agent의 claim, heartbeat, 소유권 비교, 게시 중단 및 복구 정책 | 큐 소유권 관리의 참고 사례; 신규 게시 실행은 하지 않음 |
| 배포 | main pull, web build, compose up, 공개 health 확인; DB 변경은 별도 수동 절차 | 운영 반영 전에 버전 추적과 롤백 절차 강화 필요 |
| 백업 | PostgreSQL 백업 스크립트와 복구 문서 존재 | 실제 파일 및 복원 성공 여부는 미확인 |

저장소의 현재 블로그 일정은 과거 대화의 단순 09:00/17:00 구성보다 확장돼 있다. 평일 아침 준비와 공개 시각, 17:00 글, 토요일 주간 글, 화·목 투자 공부, 일요일 다음 주 전망, 조건부 글 정책이 코드에 있다. 활성화된 환경변수, cron 등록 상태와 최근 실행 성공 여부는 VPS에서 확인해야 한다.

현재 Dockerfile과 health 응답에는 배포 Git 커밋을 직접 검증할 정보가 부족하다. 따라서 소스와 운영 배포 버전의 일치를 판정할 수 없다.

## 운영 환경에서 확인하지 못한 사항

| 항목 | 상태와 차단 원인 | 필요한 접근 |
|---|---|---|
| VPS SSH | 이전 대화의 IP로 시도했으나 현재 환경에서 `Network is unreachable`; 사용 가능한 SSH 키도 없다 | 실제 VPS에 도달하는 네트워크와 등록된 SSH 연결 |
| 실행 컨테이너와 자원 | SSH 차단으로 CPU, 메모리, 디스크, Docker 상태 미확인 | VPS 읽기 권한 |
| DB 보존 상태 | 운영 스키마, 행 수, 볼륨, 백업 파일, 복원 가능성 미확인 | 컨테이너 조회와 DB 읽기 권한 |
| cron과 블로그 최근 실행 | 소스 정책만 확인; 운영 실행 이력 미확인 | VPS cron 및 실행 기록 조회 |
| 배포 버전 | 이미지와 체크아웃을 대조하지 못함 | 이미지 메타데이터와 배포 디렉터리 조회 |
| Work와 Codex 잔여 사용량 | 이번 환경에서 잔여량을 읽는 도구가 노출되지 않음; Codex CLI도 없음 | 검증 가능한 사용량·인증 조회 수단 |
| 개인 PC가 꺼진 상태의 AI 실행 | 실제 Codex 실행기 위치 및 서버 인증 미확인 | 서버에서의 CLI 실행 검증 |

SSH 실패를 VPS 장애로 판정하지 않았다. 직접 DNS 조회도 이 환경에서 실패했지만 HTTPS 요청은 성공했다. Hostinger Mail 등 검색된 연결은 VPS 관리 기능을 제공하지 않아 대체 수단으로 사용하지 않았다.

## 실제 추가한 개발 기능

- 별도 `bg_company_v2_dev`, `bg_company_v2_test`, `bg_company_v2_staging` DB 이름만 허용하고, 운영 `DATABASE_URL`로 대체하지 않는다.
- `bg_company_v2` 스키마에 프로젝트, 작업, 의존성, 실행 시도, 사용량 상태, 이벤트를 저장한다. 기존 Prisma 스키마와 운영 Compose는 변경하지 않았다.
- 프로젝트 생성과 작업 추가에 멱등 키를 적용하고, 같은 키의 내용이 달라지면 충돌로 처리한다.
- 진행 중 또는 일시정지된 사업은 한 개만 허용한다. 전역 실행 중 작업도 한 개로 제한한다.
- Research, Plan, Build, QA, Trial Deploy, Growth의 선행 조건을 저장한다. 실패한 선행 작업을 건너뛰지 않는다.
- 트랜잭션 잠금, 실행권 토큰, 만료 시각, heartbeat, 비교 후 완료 처리를 구현했다.
- 만료된 실행권은 중단 상태로 옮긴다. 원래 프로세스의 종료가 확인되기 전에는 다른 실행을 시작하지 않는다. 종료 확인 후에도 명시적인 재개가 필요하다.
- 실패는 기본 최대 3회, 제한된 대기 시간으로 재시도한다. 완료 작업은 다시 실행하지 않는다.
- 사용량 미확인, 한도 소진, 유효기간 만료 시 실행을 막는다. 가용성 검증은 최대 15분간만 유효하다. 실제 잔여 비율을 얻은 경우 20% 이하에서 보존한다.
- 공개, 결제, 권한 변경, 유료 API 작업은 DB 제약으로 승인 대기에 고정했다. 이를 해제하는 API는 이번 단계에 제공하지 않는다.
- Git 커밋, 결과 파일 경로, 테스트 수, 관측한 토큰과 실제 비용을 저장할 구조를 만들었다. 미측정 비용은 0으로 채우지 않고 NULL로 보존한다.
- 관리자 인증이 필요한 상태 조회·프로젝트 시작·일시정지·재개 API를 추가했다. 실행권과 원문 자격증명은 API 응답에 포함하지 않는다.
- 같은 출처의 JSON 요청만 받으며, 읽는 동안 4096바이트 제한을 적용한다. 역방향 프록시 환경에는 명시적인 출처 설정을 지원한다.
- 운영 정보만 읽는 `scripts/bg-v2-audit.py`를 추가했다. 환경변수, 컨테이너 로그, 쿠키, DB 행 원문을 덤프하지 않는다.

자동 연구, Codex Builder, QA 실행 감독기, 시험 배포 실행기, 실제 방문·결제 분석기는 아직 연결하지 않았다. 실제 사업 후보 10개 조사와 MVP 제작은 다음 단계다. 기본값은 비활성이며 이 세션 종료 후 실행되는 상주 Worker나 신규 예약 작업도 없다.

## 다음 판단

Hostinger VPS를 계속 우선 사용한다. 자원 측정 전에는 1070 Ti 작업 서버 추가나 GPU 업그레이드를 결정하지 않는다. 기존 관제와 블로그는 보존하고, 새 실행기는 별도 DB·작업 공간·실행 권한으로 연결한다.

80% 사용량 배분은 목표이며, 전체 잔여량을 읽는 연결이 없는 현재 정확히 집행할 수 없다. 시간이 지났다는 이유만으로 가용 상태로 바꾸거나 재개하지 않는다. 사업 수익도 아직 측정하지 않았으며 실제 결제·정산 연결 전에 수익을 기록하지 않는다.

참고한 기술 기준: [PostgreSQL 트랜잭션 잠금](https://www.postgresql.org/docs/17/explicit-locking.html), 설치된 Next.js 16.3.1의 Route Handlers 문서, [GitHub 표준 공개 저장소 실행기 과금 기준](https://docs.github.com/en/billing/concepts/product-billing/github-actions). 검증용 Actions는 공개 저장소의 표준 Ubuntu 실행기를 사용하며 유료 API와 배포 작업을 포함하지 않는다.
