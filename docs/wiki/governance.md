# 위키 운영 규칙

## 목적

위키의 목표는 기록량을 늘리는 것이 아니라, 확인된 실패를 재사용 가능한 예방 규칙과 검증으로 바꾸는 것입니다.

## 책임

| 역할 | 책임 |
|---|---|
| 최초 발견 Agent | 현상, 시각, 실행 ID, 안전 정지 여부 기록 |
| 문제 영역 담당 Agent | 근본 원인 분석, 복구안, 예방 규칙 제안 |
| QA·윤아 | 증거 충분성, 회귀 테스트, 재현 가능성 검토 |
| 루나 | 중복 교훈 병합, 상태 전환, 주간 회고 정리 |
| CEO 병규 | 비용·공개 게시·민감 권한·핵심 정책 변경 승인 |

## 교훈 상태

| 상태 | 의미 | 다음 상태 조건 |
|---|---|---|
| `observed` | 실패를 확인했지만 원인 또는 복구가 미확정 | 영향 범위와 안전 정지 확인 |
| `contained` | 잘못된 외부 결과를 막았고 임시 복구가 있음 | 근본 원인과 예방 규칙 확정 |
| `prevented` | 예방 규칙과 검증이 반영됨 | 실제 운영 또는 재현 테스트 통과 |
| `verified` | 예방 효과를 운영에서 확인함 | 재발 시 다시 `observed` 또는 `contained` |
| `archived` | 기능 제거 등으로 더 이상 적용되지 않음 | 대체 결정 또는 제거 근거 연결 |

## 실패 기록 절차

1. 오류 코드, 단계, 콘텐츠 유형을 조합해 재현 가능한 `fingerprint`를 만듭니다.
2. 교훈 원장에서 같은 `fingerprint`를 검색합니다.
3. 기존 항목이면 `last_seen`, `recurrence_count`, 재발 기록을 갱신합니다.
4. 새 원인이면 템플릿으로 교훈을 만들고 담당자와 심각도를 지정합니다.
5. 비밀키 원문, 로그인 정보, 개인정보, 원문 프롬프트의 민감 데이터는 남기지 않습니다.
6. 예방 규칙이 코드·설정·프롬프트를 바꾸면 결정 기록과 회귀 테스트를 함께 연결합니다.

일반 `ErrorOccurred` 이벤트와 주식 블로그 스케줄러의 `failed`·`partial_failed` 상태는 운영 학습 원장에 자동 기록됩니다. 같은 실행의 중복 이벤트는 correlation ID로 한 번만 집계하며, 앞 단계 실패에 따른 단순 `SKIPPED_AFTER` 결과는 새로운 근본 실패로 집계하지 않습니다.

## fingerprint 규칙

형식은 소문자 kebab-case를 사용합니다.

```text
<제품영역>:<파이프라인단계>:<안정적인-원인-또는-오류코드>
```

예:

```text
stock-blog:reference-preflight:missing-verified-market-data
stock-blog:quality-gate:editorial-contract-too-short
```

날짜, 실행 ID, 일시적인 메시지 전체는 `fingerprint`에 넣지 않습니다. 그것들은 재발 기록에 남깁니다.

## 주간 회고

루나는 매주 다음 항목을 한 번 검토합니다.

- 새로 생긴 `observed`·`contained` 교훈
- 7일 안에 두 번 이상 발생한 `fingerprint`
- 회귀 테스트가 없는 예방 규칙
- `prevented` 상태지만 운영 검증이 끝나지 않은 항목
- 코드·설정과 Agent 운영 지도의 불일치

반복 실패가 발견되면 단순 재시도 횟수를 늘리기 전에 입력 데이터, 책임 경계, 품질 게이트, 복구 정책 순서로 점검합니다.

7일 안에 같은 `fingerprint`가 2회 이상 확인되면 루나 명의의 운영 개선 승인 요청을 자동 생성합니다. 승인된 예방 규칙만 해당 영역·Agent의 실행 입력에 최대 5개까지 포함합니다. 교훈은 시장 사실이나 외부 실행 지시로 사용하지 않으며 현재 검증 데이터와 하드 안전 규칙이 항상 우선합니다.

`verified` 상태는 다음 조건이 모두 있을 때만 허용합니다.

- 승인 상태가 `approved`
- 적용할 예방 규칙
- 회귀 테스트 또는 명시적인 수동 검증 절차
- 테스트 통과나 운영 재검증 증거

## 변경 승인 경계

다음 변경은 CEO 병규의 승인이 필요합니다.

- 자동 게시 또는 외부 전송 범위 확대
- 비용 한도, 모델, 동시성의 유의미한 증가
- 인증·비밀정보·브라우저 프로필 처리 변경
- 품질 게이트 완화 또는 안전 정지 우회
- Agent의 최종 승인 권한 변경

문구 정리, 깨진 링크 수정, 이미 승인된 정책의 사실 갱신은 루나 검토로 처리할 수 있습니다.

## 문서 품질 규칙

- 추정은 사실과 분리해 `미확정`으로 표시합니다.
- 로그 전체 대신 필요한 시각·오류 코드·실행 ID만 기록합니다.
- 링크는 가능한 한 저장소 내부의 코드, 테스트, Runbook을 가리킵니다.
- 해결책에는 담당자와 검증 방법이 반드시 있어야 합니다.
- 문서 변경 후 `npm run test:wiki`를 실행합니다.
